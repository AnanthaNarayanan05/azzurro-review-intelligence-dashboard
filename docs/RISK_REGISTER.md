# Risk Register

Likelihood / Impact: L = low, M = medium, H = high.

| # | Risk | Category | L | I | Mitigation |
|---|---|---|---|---|---|
| R1 | Real dataset not yet provided; its format is unknown | Data availability | H | H | Flexible column mapping; build on flagged synthetic data; schema designed to adapt; re-tune once data arrives |
| R2 | No authorised Booking.com API access; the site's terms prohibit automated collection | API dependency / legal | H | M | **Decision (Phase 3):** no scraper. File import is the only collection route; provenance recorded per import; the pipeline accepts any future authorised source. See `REQUIREMENTS.md` |
| R3 | Export lacks fields (no review ID, no language, single text field) | Data | M | M | Content-hash dedup; language detection; `body_text` path; analytics degrade gracefully and report what is missing |
| R4 | Multilingual reviews reduce English-only NLP coverage | AI/NLP | M | H | Measure language mix first; multilingual model if needed; report excluded counts transparently |
| R5 | Sentiment/aspect accuracy lower than expected | AI/NLP | M | H | Labelled-sample evaluation; tune lexicon/thresholds; consider transformer only if it measurably helps |
| R6 | LLM fabricates statistics or evidence (hallucination) | AI | M | H | LLM optional and off by default; evidence-only input; grounding validator; template fallback |
| R7 | Paid API costs | Cost | L | M | No paid service without cost estimate and approval; free deterministic path is complete on its own |
| R8 | Small samples lead to misleading comparisons/trends | Analytics | H | H | Show n everywhere; minimum-sample thresholds; significance tests; "insufficient data" states |
| R9 | Rating vs text sentiment confusion in interpretation | Analytics | M | M | Keep separate measures; label clearly in UI; document |
| R10 | Transformer dependencies too heavy for free hosting | Performance/deploy | M | M | Store NLP results; run heavy models offline/at import; VADER on hosted instance |
| R11 | Large uploads exhaust memory | Performance | L | M | Size/row limits; chunked processing; streaming read where possible |
| R12 | Private review data or secrets committed to Git | Security | M | H | `.gitignore` for data/DB/env; review staged changes before each commit; only synthetic data tracked |
| R13 | Malicious upload (formula injection, zip bombs in XLSX, wrong type) | Security | L | M | Extension + content checks, size limits, openpyxl read-only mode, never evaluate formulas, escape on export |
| R14 | Hosted demo exposes data publicly | Security/privacy | M | H | Deploy with synthetic data only unless approved; optional access protection; confirm with project owner |
| R15 | Free-tier hosting limits change (sleep, DB expiry) | Deployment | M | M | Check current limits at Phase 8; document; keep local run fully supported |
| R16 | Scope creep vs assessment deadline | Delivery | M | H | Phase gates; core analytics before optional LLM; ask for deadline |
| R17 | SQLite → PostgreSQL behaviour differences | Technical | L | M | SQLAlchemy portable types; **mitigated in Phase 8**: the full suite (334 tests) passes on PostgreSQL via `TEST_DATABASE_URL`, and all migrations apply. A remote managed database has not been tried |
| R18 | Uploaded export contains guest names or other personal data | Privacy | M | H | Guest names are not importable; unmapped columns are not stored; uploads are deleted after commit; imports can be undone |
| R19 | Day/month ambiguity silently misdates reviews | Data quality | M | M | Ambiguous dates are rejected unless the user chooses an order; the choice is stored on the batch |
| R20 | The declared source name on an import is wrong or misleading | Provenance | M | M | Shown as the uploader's statement, not verified; synthetic data is forced to `synthetic-demo` and counted separately |
| R21 | SQLite write contention ("database is locked") during import | Technical | L | M | Single transaction, 3 retries, full rollback on failure (tested); PostgreSQL planned for hosting |
| R22 | Neutral-sentence rule (a neutral sentence takes the polarity of its Booking.com box) and VADER thresholds mislabel mentions | AI/NLP | M | M | Rule is documented and applies to mentions only; evaluate on the labelled sample in Phase 7 and revise or remove it; evidence sentences are always shown |
| R23 | Keyword aspects miss implicit mentions, so aspect counts understate real issues | AI/NLP | H | M | Documented limit; mention counts are reported with `low_sample` flags; measure recall in Phase 7; embedding/zero-shot only if evaluation justifies it |
| R24 | Many property x aspect x window comparisons yield chance "significant" results | Analytics | M | M | Practical-size thresholds as well as intervals; minimum samples; wording presents indications with n, not proof |
| R25 | Analysis fails or is skipped, leaving reviews unscored and dashboards incomplete | Technical | L | M | Reviews are counted as "waiting" on every figure; failed runs are recorded and roll back cleanly; re-run from Settings; import never fails because of analysis |
| R26 | A dashboard number is misread: small samples, mixed genuine/synthetic data, or an unfinished period shown as fact | Analytics | M | H | Every figure shows its n and a "Low sample" flag (threshold comes from the API); a banner appears whenever the data is not genuine-only; trend points for unfinished or thin periods are hollow; a best/worst property is named only when the API says it is ranked |
| R27 | Hand-written charts have layout, accessibility or browser bugs that a library would have avoided | Technical | M | L | Each chart has a table view, written labels and hover detail, and component tests; checked in the browser at desktop width. Responsive checks, a keyboard/screen-reader audit and visual regression remain for Phase 7 |
| R28 | Insights are read as proven causes or as advice, when they only describe patterns in what guests wrote | Analytics / interpretation | M | H | Wording says "mentioned" and "complaints", never "caused"; suggested actions come from a fixed catalogue and are labelled suggestions; every insight shows its counts, period and an evidence-strength label, and links to the exact reviews |
| R29 | Many rules over properties x aspects x windows produce chance insights (multiple comparisons) | Analytics | M | M | Inferential rules need an interval excluding zero, a practical-size gap and 30 observations per side; the generation result reports how many combinations were checked and skipped; not corrected for multiple testing, so insights are indications |
| R30 | Insight thresholds (40 % complaint, 80 % strength, 30 % opportunity, strength grades) are starting points chosen by judgement; one was changed after looking at the demo data | AI / Analytics | M | M | Thresholds live in one file and are stored with every insight; documented as unvalidated; revisit with the real dataset and human feedback in Phase 7 |
| R31 | Stored insights go out of date after an import, deletion or re-analysis and are trusted anyway | Data quality | M | M | Each generation stores the analysis run and review count; the API reports `stale` and the page shows an "out of date" warning with a working Regenerate button; the Overview teaser says so too |
| R32 | Insights made from synthetic demo data are mistaken for real findings | Transparency | M | H | `data_scope` is stored on every insight and shown on every card and by the page banner; synthetic scope is never the default; scopes are generated and replaced independently |
| R33 | Sentiment and aspect accuracy is unknown: the tooling exists but no human-labelled sample has been scored | AI/NLP | H | H | Do not claim accuracy anywhere; `docs/LABELLING_GUIDE.md` and `scripts.evaluate_models` are ready; the owner (or a nominated person) labels ~150-200 genuine reviews; report results and revise the neutral-sentence rule and lexicon if they are poor |
| R34 | The performance figures come from repeated synthetic text, SQLite, in-process calls and one laptop, so real behaviour may differ; ratings are aggregated in Python, so the overview and comparison endpoints (0.7-0.8 s at 50k reviews) have little headroom | Performance | M | M | Figures are documented with these caveats; if data grows or PostgreSQL is used, move the rating aggregation into SQL and re-run `scripts.benchmark`; hosting limits checked in Phase 8 |
| R35 | The browser test and accessibility audit cover one browser (Chrome) and automated rules only, so screen-reader and keyboard-only problems may remain | Quality / accessibility | M | M | Documented as not covered; a manual keyboard and screen-reader pass is recommended before any public release; the axe audit runs on every page in `npm run e2e` so regressions are caught |
| R36 | `npm audit` reports 4 moderate advisories (one `minimatch` denial-of-service issue reached through the `shadcn` component CLI); they are in development tooling only (`npm audit --omit=dev` reports 0) and the suggested forced fix is a breaking change | Security / supply chain | L | M | Not force-fixed; the CLI is not shipped or run in production; revisit at deployment time and upgrade deliberately; no secrets or user accounts exist in the app |
| R37 | The public demo is fully interactive and has no login (the owner's choice, 2026-11-24), so anyone with the address can import, delete or regenerate data | Security / privacy | M | H | Host only synthetic data; uploads are capped at 5 MB and 5,000 rows on the hosted API; Settings can clear and reload the demo; share the address privately or use the host's password protection; a read-only mode or access code is not built and needs the owner's decision (docs/DEPLOYMENT.md) |
| R38 | A free API plan sleeps, has limited memory and runs a single instance (uploads are held on local disk between preview and import), so first requests are slow and a second instance would break imports | Deployment | M | M | Documented; run exactly one instance; the UI shows a retryable "Service unreachable" state; memory use on the host plan is untested |
